# ChatGPT生成ファイルのDropboxへの安全な受け渡し手順

- 文書種別：汎用実行手順書
- 作成日：2026-10-18（Asia/Tokyo）
- 想定保管先：ChatGPT Library `/references/chatgpt-file-handoff-to-dropbox.md`
- 実証範囲：ChatGPT Libraryまたは会話の実ファイルをChatGPTの正式な生成添付ファイルとして用意し、Dropbox接続の `upload_file` に渡して新規保存する経路。2026-10-17（JST）に小ファイルおよびカクヨム週間調査の本番3ファイルで成功。その他の外部サービスやすべての環境での動作を保証するものではない。

## 1. 適用対象と優先順位

- ユーザーの明示的なDropbox保存・同期依頼がある場合に参照する。自動タスクの保存方針や同期の許可を勝手に変更しない。
- 事前に対象データ、最新正本、ファイル名、正確なDropbox保存先フルパス、保存先フォルダ、重複・競合の有無を確認する。
- 当該会話のユーザー指示・ファイル保全規則が本手順より厳しい場合はそれを優先し、危険な代替手段を試さず停止する。
- 特に、既存の同名ファイルを更新する場合は、上書きする前に元ファイル**そのものを同じディレクトリ内で改名してバックアップを作成**する。複製はバックアップの代わりにしない。

## 2. 成功した正式な受け渡し経路

1. **出典の特定：** Library上のファイルなら所在とファイルIDを確認し、必要なコミット・バージョン・参照先と整合させる。対象の内容が確定していなければ停止する。
2. **原本の取得：** Libraryのファイルを元のバイト列のまま作業環境へ取得する。単なるテキスト抽出は、末尾改行・エンコーディングなどを変える場合があるため、バイト同一性が必要なら生ファイルを使う。
3. **完成版生成：** UTF-8など指定の形式で、Dropboxに保存する完成版の実ファイルをChatGPTが生成する。内容、バイト数、必要に応じてSHA-256を検証する。再生成の過程で変更が入っていないことを確かめる。
4. **正式ファイルIDの取得：** **その実行で生成された会話の添付ファイル**に対してChatGPTが発行した実在の `file_...` 形式のIDを確認する。過去のID、推測で作ったID、ファイル名、`/mnt/data/...` のローカルパスをDropboxへのアップロード元に使わない。ファイル生成の成功と添付ファイルID登録の成功は区別する。
5. **アップロード：** Dropbox接続 `upload_file` の `destination_path` にDropbox側の完全パス（ファイル名を含む）を指定し、`source_file` には正式に取得した当該生成ファイルIDを受け渡す。2026-10-17に成功した実行では、ChatGPT側の受け渡し機構がこのIDをファイルとして扱った。APIの型・アダプター仕様が異なる環境では、引数を捏造せず停止する。
6. **完了確認：** 応答が `in_progress` なら、返された `operation_id` を `check_upload_file_status` へ渡して `completed` まで確認する。途中応答を成功とみなさない。
7. **独立照合：** Dropboxに保存されたファイルを改めて特定し、サイズおよび可能な範囲で内容・ハッシュを原本と照合する。Dropboxの `fetch` が返す抽出テキストは改行が増える場合があり、それだけでバイト不一致と決めつけない。原本のバイト列から計算した**Dropbox Content Hash**とDropbox側のContent Hashを比較できれば、サイズと併せてバイト同一性を確認できる。Content Hashは通常のファイル全体のSHA-256とは異なる計算法なので混同しない。
8. **報告：** 保存先、サイズ、実際の検証結果、既存データへの変更の有無、未完了部分を明記する。

## 3. 保存先に既存ファイルがあるとき

### 同名なし

同名ファイルがないことと親フォルダの存在を確認し、新規アップロードする。バックアップ改名は不要。

### 同名あり・内容一致

原則としてアップロードを省略し、既存ファイルを同期済みとして扱う。ただし一致の根拠（サイズ・ハッシュ・内容など）を記録する。

### 同名あり・内容相違

1. **更新版を完成させ、正式な添付ファイルIDまで取得する。** 準備ができないなら既存ファイルに触れない。
2. 同じディレクトリ内のバックアップ一覧を確認する。元ファイル `name.ext` に対し `name.backup-YYYY-MM-DD-NN.ext`（拡張子なしなら `name.backup-YYYY-MM-DD-NN`）という未使用の連番を決める。日付はバックアップ作成日、NNは01からの2桁連番。
3. Dropbox上の元ファイル**そのものを改名**する。バックアップ複製や直接上書きに代替しない。
4. 改名完了と元データのバックアップ側での存在を確かめる。
5. 元の正確なパス・元のファイル名へ新しい完成版をアップロードする。
6. 新版の存在とサイズ・ハッシュ／本文を確認する。バックアップは保持する。

改名に失敗した場合は、元ファイルに手を加えず中止する。改名後の新規保存に失敗した場合はバックアップと未完了状態を報告し、上書き・削除などの破壊的操作は避ける。安全な復旧条件が明確でない限り独断で巻き戻さない。

## 4. Dropbox Content Hashの照合方法

Dropbox Content Hashは、ファイルを最大4 MiB（4,194,304バイト）のブロックに分割し、各ブロックのSHA-256ダイジェストを連結して、その連結バイト列をさらにSHA-256した値。通常の `SHA256(ファイル全体)` とは異なる。

Pythonで元ファイルから計算する例：

```python
from pathlib import Path
import hashlib

def dropbox_content_hash(path: str) -> str:
    h = hashlib.sha256()
    with Path(path).open('rb') as f:
        while block := f.read(4 * 1024 * 1024):
            h.update(hashlib.sha256(block).digest())
    return h.hexdigest()
```

Dropbox側で取得可能なContent Hashと計算結果が一致した場合に限り「Content Hash一致」と報告する。ハッシュを取得できない場合は「未照合」とし、アップロード成功だけを内容照合成功と書かない。

## 6. 停止条件

次のいずれかならアップロード・改名・更新を中止する。

- 出典の正本、データ内容、保存先、ユーザーの許可が不明確。
- 生ファイルを取得できない、サイズや必要なハッシュに不一致がある。
- **当該実行で発行された正式な生成添付ファイルIDを取得できない。**
- `source_file` に渡す方法が正規のツール仕様と一致しない。
- 保存先親フォルダが存在しない、同名ファイルの競合を解消できない。
- バックアップ名の競合、元ファイルの改名失敗、改名検証失敗。
- `upload_file` が失敗または未完了、Dropboxの独立読戻し・照合に失敗。

既存データの保全を優先し、「保存済み」「同期済み」を未検証のまま主張しない。残った成果物と復旧に必要な操作を具体的に報告する。

## 7. 他の用途への適用

- 本手順の**ファイル生成・当該生成IDの確認・保存後独立照合・既存ファイル保全**という原則は別案件でも参考にできる。
- `source_file` の形や生成ファイルから外部サービスへの受け渡し可否はコネクター・実行環境によって異なる。Dropboxで成功したという事実だけで、Google Driveや他サービスのアップロードにも同じ操作を流用しない。必ず対象ツールの入出力仕様を確認する。
