# 指示

## このプロジェクトの目的

- `Dropbox\MGMT.md` の `priority` に登録された作業について、Dropbox 上の対応する作業内容と GitHub リポジトリを照合する。
- 現在日の更新では、確認できた Dropbox の変更を対応する GitHub リポジトリへ commit し、通常の push まで行う。
- push 済みの GitHub コミットを、Notion の `作業記録` に日付別の実績として反映する。
- Dropbox は作業内容の参照元として扱い、ユーザーが明示的に依頼した場合を除いて変更しない。

## 対象と範囲

- ユーザーが作業記録の更新を依頼した場合に実行する。
- 対象日または期間が指定されている場合はそれに従う。指定がない場合は、ユーザーの現在のローカル日付を対象にする。
- `Dropbox\MGMT.md` の `priority` 配下に現在登録されている項目だけを対象候補とする。空の優先度は無視する。
- 自動 commit / push は、対象期間に現在のローカル日付が含まれる場合だけ行う。過去の日付だけを対象にする依頼では、既存コミットの記録だけを行う。
- ユーザーが明示的に Git の変更を行わないよう求めた場合は、commit / push を行わない。
- 対象期間に push 済みのコミットがないリポジトリは Notion に記録しない。

## 情報源

### Dropbox

- `Dropbox\MGMT.md` の `priority` から対象候補を取得する。
- Dropbox 内のフォルダまたはファイルの場所を特定する前に、必ず `Dropbox\ai\ChatGPT\etc\sources.md` を索引として参照する。
- 索引が示すフォルダでは、必要に応じて直下の `README.md` を確認し、対象候補に対応する作業内容を特定する。
- `op` に数字が続く項目は `Dropbox\scribe\novel\<項目名>`、`ssop` に数字が続く項目は `Dropbox\scribe\novel\opss\<項目名>` を確認する。その他の項目は `sources.md` の用途と `README.md` に基づいて対応フォルダを特定する。
- Dropbox のファイルと GitHub のリポジトリ内ファイルの対応は、フォルダの用途、既存のディレクトリ構造、ファイル名または内容から一意に確認できる場合だけ採用する。対応を推測で決めない。

### GitHub

- 接続されている GitHub アカウントが所有し、書き込み権限を確認できるリポジトリだけを対象にする。
- `priority` の項目とリポジトリは次の規則で対応づける。
  - `op` に数字が続く項目 → 同名のリポジトリ。例: `op78` → `op78`
  - `ssop` に数字が続く項目 → `opss`
  - `物語構築の研究` → `research-of-narrative-construction`
  - `文彩の研究` → `research-of-literary-ornamentation`
  - `世界設定の研究` → `research-of-world-building`
  - `小説の制作手法` → `novel-creating-method`
  - `等身大の点と点委員会` → `life-sized-dot-to-dot-committee`
- 上記で対応できない項目は、`sources.md` と所有リポジトリから候補を探す。一意に特定できない場合は処理しない。
- 複数の対象候補が同じリポジトリに対応する場合は、そのリポジトリを1回だけ処理する。

### Notion

- `作業記録` データベースだけを更新する。
- 更新前に現在のスキーマを確認し、`名前` がタイトル、`日時` が日付プロパティであることを確認する。異なる場合は書き込まず報告する。

## 自動 commit / push の規則

- 作業記録の更新依頼には、ここで定める範囲の通常の commit と push を行う許可が含まれるものとする。
- Dropbox の対応フォルダを参照し、対応するリポジトリの対象ブランチとの差分を確認する。フォルダ直下がリポジトリ直下に対応することを確認できない場合は、ファイルを配置または移動しない。
- Dropbox で確認できた新規または変更済みのファイルだけを対象にし、対応関係を確認できない既存のローカル変更は commit に含めない。
- Dropbox 上で見つからないことだけを根拠に、リポジトリ内ファイルを削除しない。削除が必要な場合は、ユーザーに確認する。
- 秘密鍵、アクセストークン、パスワード、`.env` などの認証情報を含む可能性があるファイルは commit しない。対象に含まれる場合はファイル名と理由を報告する。
- 同じリポジトリ内で、変更の目的を一つの要約で正確に表せるファイルは一つの commit にまとめる。目的が異なる変更、または一つの要約では正確に表せない変更は別の commit にする。
- 各 commit メッセージは、変更内容を表す日本語の要約だけで作成し、全角・半角を問わず20文字以内にする。接頭辞、本文、改行、推測による補足は付けない。
- commit 前に、対象ファイルと差分がメッセージの内容に一致し、無関係なファイルが含まれないことを確認する。
- 各リポジトリで今回作成した commit を、現在のブランチの設定済み upstream へ通常の push で送信する。force push、履歴の書き換え、amend、reset、stash、rebase、ブランチ切替、設定変更は行わない。
- push 前に upstream との差分を確認する。未確認のローカル commit、リモートの先行、競合、保護ブランチ、認証エラー、upstream 未設定などにより安全に push できない場合は、そのリポジトリで commit / push を中止して理由を報告する。
- commit 後に push が失敗した場合は commit を取り消さず、その commit を Notion に記録しない。失敗理由と未 push であることを報告する。

## 作業手順

1. 対象日または期間を確定する。GitHub のコミット時刻はユーザーのローカルタイムゾーンへ変換して日付を判定する。タイムゾーンを取得できない場合は `Asia/Tokyo` を使う。
2. `Dropbox\MGMT.md` の `priority` 配下から対象候補を取得する。`Dropbox\ai\ChatGPT\etc\sources.md` を参照して各候補の Dropbox 上の作業場所を特定し、上記の規則で GitHub リポジトリへ対応づける。
3. 対象期間に現在のローカル日付が含まれる場合は、各リポジトリについて Dropbox の対応フォルダと GitHub の対象ブランチを照合する。変更対象、対応関係、書き込み権限、upstream、push の安全性を確認できたリポジトリだけ、変更内容ごとに commit を作成して push する。
4. push が成功したリポジトリについて、対象期間内の GitHub コミットを取得する。取得件数に上限やページ分割がある場合は、対象期間を取りこぼさないところまで確認する。
5. コミットをリポジトリとローカル日付の組み合わせごとに、古い順でまとめる。
6. Notion の `作業記録` で、同じ `名前` と `日時` を持つアイテムを確認する。
   - 0件なら新規作成する。
   - 1件ならそのアイテムを更新する。
   - 2件以上なら対象を推測せず、そのリポジトリと日付の更新を中止して重複を報告する。
7. 各アイテムに記入するコミットメッセージを次の規則で選ぶ。
   - GitHub で確認したメッセージから前後の空白だけを除いた文字列を、重複判定に使う。
   - 今回の対象コミット内で同じ文字列が複数ある場合は、最も古いコミットのメッセージだけを採用する。
   - 既存アイテムを更新する場合は、本文内の箇条書きに同じ文字列が1件でもあれば、そのメッセージを追加しない。
   - 重複判定は同じ `名前` と `日時` のアイテム内だけで行う。別の日付または別のリポジトリの記録は重複として扱わない。
8. 新規作成時は、`名前` にリポジトリ名、`日時` にコミットのローカル日付を設定し、選んだコミットメッセージを本文へ箇条書きで記入する。既存アイテムの更新時は既存本文を保持し、選んだ未記録のメッセージだけを末尾に追加する。
9. 更新後に対象アイテムを再確認し、`名前`、`日時`、本文が意図どおり反映され、今回記入したメッセージに重複がないことを確認する。

## 記録規則

- 1つのリポジトリについて、同じ日付には原則として1つのアイテムだけを使う。
- `名前` には `owner/repository` ではなくリポジトリ名だけを記録する。
- `日時` には時刻を含めず、コミットを行ったローカル日付を記録する。
- 本文のコミットメッセージは、古いコミットから新しいコミットの順に箇条書きで並べる。
- コミットメッセージは要約、言い換え、補完をせず、GitHub で確認できた文字列を使う。前後の不要な空白だけは除いてよい。
- 同一アイテム内では、同じメッセージのコミットが複数あっても、同じ文言を複数の箇条書きにしない。
- 再実行時は、既存本文の箇条書きと今回の対象メッセージを照合し、記録済みの文言を追加しない。
- 既存本文に重複したコミットメッセージや GitHub 由来でない記述があっても、削除、置換、整形しない。
- リポジトリの最終更新日時だけでは作業実績と判定せず、実際に push 済みのコミットを根拠にする。

## 例外・制限

- `Dropbox\MGMT.md`、`Dropbox\ai\ChatGPT\etc\sources.md`、対象の Dropbox ファイル、GitHub、Notion のいずれかを確認できない場合は、その情報に依存する commit、push、Notion 更新を行わず、確認できなかった情報源を報告する。
- リポジトリまたは Dropbox の作業場所を一意に特定できない項目、同一日付に同名の Notion アイテムが複数ある項目、コミット取得が不完全な項目は、その項目を更新せず理由を報告する。
- Git 操作の書き込み権限、対象ブランチ、upstream、差分の安全性を確認できない場合は、GitHub を変更しない。
- Notion では `作業記録` 以外を変更しない。
- 確認できないリポジトリ名、Dropbox のファイル対応、コミット、日時、既存記録を推測で補わない。

## 出力形式

- 通常は、対象日または期間、commit・push したリポジトリ名と件数、Notion に追加したコミット件数、重複のため追加しなかったコミットメッセージ数、処理しなかった項目と理由だけを簡潔に報告する。
- commit は成功したが push できなかった場合は、未 push のリポジトリ名と理由を必ず報告する。
- ユーザーが求めない限り、確認した全ファイル、全コミット、内部の検索手順を列挙しない。
