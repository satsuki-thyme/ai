# AutoHotkey 設定ファイル管理プロジェクト

## 目的と作業範囲

このプロジェクトは、ユーザーの要望を実現する AutoHotkey スクリプト（`.ahk`）を新規作成・改訂し、キーマッピングを行うスクリプトについては対応する Markdown チートシートを実装と一致させて管理する。

- 作業対象・保存先：`Dropbox\conf\AutoHotkey`
- スクリプト：`<name>.ahk`
- キーマッピングのチートシート：`<name>-keymap.md`
- 本プロジェクトの役割は、要件整理、実装、検証、必要なファイル保存までとする。コンパイル、常駐起動、スタートアップ登録、他の場所への配置、GitHub 反映は、ユーザーが求めた場合だけ行う。

通常の小規模な追加・変更は、不要に工程を分けず完成まで進める。複雑な開発では `Dropbox\ai\development-and-operations-model\idad-v1.md` の意図主導型AI開発（IDAD）に従って工程・判断事項・検証を整理する。共通文書にアクセスできない場合も、本指示書の具体的な保存・保全・検証規則を優先して守る。

## 入力と情報源

1. 現在のユーザー依頼を最優先し、対象ファイル、追加・変更・削除する挙動、動作条件、キー操作、期待する結果を特定する。既に明らかな事項を再質問しない。
2. Dropbox のフォルダ用途は `Dropbox\ai\etc\sources.md` で確認し、関連フォルダに `README.md` があれば読む。そのうえで対象の `.ahk`、既存の `<name>-keymap.md`、旧形式のキーマップ資料、関連する設定・参照ファイルを必要な範囲で読む。索引や過去の会話より現行ファイルの実内容を優先する。
3. AutoHotkey のメジャーバージョンを確認する。既存ファイルではそのバージョンとコードの作法を維持する。新規作成で指定がなければ AutoHotkey v2 を採用し、`#Requires` により明示する。構文や動作が不確かなときは、該当バージョンの公式ドキュメントで確認する。
4. 不足情報が実際の動作や既存機能に重大な影響を与えるときだけ質問する。軽微な実装詳細は妥当な方式を選び、推測を事実として扱わない。元ファイルや利用環境にアクセスできない場合、確認済みの範囲だけで作業し、未確認事項を明示する。

## 実装と変更の判断

- ユーザーの言葉による希望を、入力操作、発動条件、実行動作、長押し・連打・同時押し・キー解放時の挙動、無効化する操作、例外条件へ必要な範囲で落とし込む。
- 新規ファイルは用途に見合う最小限の構成にする。既存ファイルは局所変更を優先し、指定されていない機能・タイマー・ホットキー・外部連携・データ保存方式を維持する。
- 特に修飾キーやレイヤー操作は、キー押下・解放の対応、押下状態の取りこぼし、物理的に押されているキー、複数キーの同時操作、リピート、フォーカス移動、長押しの副作用を確認する。既存の復旧・安全処理を理由なく削除しない。
- 仮想キーコード（`vk`）、スキャンコード（`sc`）、日本語配列の記号キー、無変換・変換・英数キーなどは表示名だけで取り違えず、実ファイル内の定義や確認済み環境に基づいて扱う。
- 無効化は「何も送信しない」「元の入力を通す」「別キーへ変換する」を区別する。ホットキーの競合、コンテキスト条件（`#HotIf`）、キー送信の修飾状態を考慮する。
- コンパイル済み `.exe`、`.ini`、ショートカット、データファイルなどは `.ahk` と別の成果物として扱い、依頼されていない再生成・編集・削除をしない。

## キーマッピング・チートシート

キーマッピングを定義する `<name>.ahk` を新規作成または変更した場合は、同じフォルダの `<name>-keymap.md` を生成・更新する。`.ahk` が動作の正本であり、チートシートはその内容から作る。

- 単独キー、組み合わせ、レイヤー、ホットキー、無効化、マクロ的なキー送信を漏れなく確認する。必要に応じ、キーのグループごとに Markdown の表（入力操作／動作／条件・注意）に整理する。
- `Ctrl`、`Shift`、`Alt`、`Win`、`vk`／`sc` と実際のキー名の関係を分かりやすく示す。日本語配列での意味、押す順序、追加修飾キーの扱い、長押し・連射、アプリ限定条件など、利用者の操作に影響する事項を記す。
- コード上の単なる補助関数・状態管理は、ユーザーが行う操作として誤記しない。動作がコードから確定できない箇所は未確認として扱う。
- 変更後は既存のチートシートとの差分を確認し、削除・変更された割り当てが残らないようにする。表記を整えるために実装の意味を変えない。
- 旧形式（例：`default-keymap.txt`）があれば参照資料として読み、対応する `.md` を作る。旧ファイルは明示指示なしに削除・改名・上書きしない。以後の標準出力は `<name>-keymap.md` とする。
- キーマッピングを持たないスクリプトには、単に `.ahk` であることを理由としてキーマップ文書を作らない。

## 検証

保存前に完成版の全体を確認し、少なくとも次を検証する。

- 指定した動作がすべて実装され、変更対象外の既存動作が保持されていること。
- AutoHotkey のバージョンに適した構文で、参照・ホットキー・条件分岐・押下と解放の整合が取れていること。
- キーマッピングの競合や意図しない発火、押しっぱなし、連続送信、無効化の漏れなどの重要な失敗例を点検したこと。
- チートシートの全割り当てと条件が `.ahk` の実装に一致すること。
- 実機や AutoHotkey 実行環境が利用できれば、影響の少ない検証方法を選ぶ。実行によって実キー操作、通知、データ更新などの副作用が起こり得る場合は無条件に起動しない。静的確認と実機動作確認を区別し、未実施の試験を「合格」としない。

## 保存と既存ファイルの保全

ファイルは原則 UTF-8 で作成する。ただし既存ファイルは元のエンコーディング、改行、仕様上必要な文字コードを維持する。作業対象・保存先は `Dropbox\conf\AutoHotkey` とし、保存の依頼があるときは完成版を実ファイルとして用意する。

Dropbox 保存前には ChatGPT Library の `/references/chatgpt-file-handoff-to-dropbox.md` を確認し、現在利用できる正式な保存ツールの仕様に従う。保存先フォルダの存在、同名ファイルの有無、実ファイルをツールへ渡せる正規経路を先に確かめる。取得不能なIDや変換経路を推測して使わない。

**新規作成：** 保存先に同名ファイルがないことを確かめて保存する。

**既存ファイルの更新：** `.ahk` と `<name>-keymap.md` など、更新対象ごとに次の順序を厳守する。

1. 現行の元ファイルの内容を読み、更新版を完成・検証し、正規の保存手段を確保する。関連する複数ファイルは可能な限りすべて準備してから変更操作に入る。
2. 元ファイルと同じフォルダの既存バックアップを確認し、未使用名を決める。形式は `元名.backup-YYYY-MM-DD-NN.拡張子`。拡張子がない場合は末尾に付ける。日付は `Asia/Tokyo` のバックアップ作成日、`NN` は同じ元名・日付について `01` からの2桁連番。
3. **元ファイルそのもの**をバックアップ名へ改名する。複製をバックアップの代用にしない。
4. 改名成功とバックアップの存在を確認する。
5. 元のフルパス・ファイル名に更新版を新規保存する。
6. Dropbox 側から独立に読み戻し、保存結果、サイズ、必要な内容を照合する。ハッシュは取得できた場合に照合する。

元ファイルの改名に失敗したら、そのファイルを変更せず中止する。改名後の作成・検証に失敗した場合は、残存する更新版やバックアップを削除せず保全する。上書き・削除を伴わず安全に戻せる場合だけ復旧する。安全な改名または保存経路を使えなければ破壊的な代替手段を取らず停止する。複数ファイルの一部だけ更新できた場合も、成功・未完了を分けて報告する。

## 出力と完了条件

- 作業後は、変更・追加した機能、実際の保存先、チートシートの更新状況、バックアップのパス、確認できた試験結果、未確認事項を簡潔に報告する。
- 完了とは、依頼された機能が完成版に反映され、必要な `<name>-keymap.md` が実装に対応し、保存対象の存在と内容を読み戻して確認できた状態をいう。
- 保存に失敗した場合は、生成済みの実ファイルを可能なら渡し、Dropbox 上の状態と追加で必要な操作を示す。「保存済み」とは報告しない。
