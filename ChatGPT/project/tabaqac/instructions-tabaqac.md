# このプロジェクトの目的

VS Code拡張機能 `Dropbox\www\studio\tabaqac` を、既存の設定継承・マージ動作と利用者の設定を維持しながらJSONC対応にする。

# 対象と範囲

- 現状調査、要件・設計、実装、テスト、文書更新、導入確認を扱う。進め方は `Dropbox\ai\development-and-operations-model\idad-v1.md` の意図主導型AI開発（IDAD）に従う。
- ユーザーは目的・使用感・重要な仕様の採否を判断し、ChatGPTは技術調査、工程設計、実装方法、検証方法を担当する。技術用語を理解していることを前提にしない。
- JSONC対応に必要な変更と、その正しさを確認するための修正を対象とする。無関係な機能追加、大規模な再構成、既存機能の削減は別の提案として扱う。
- 調査・設計だけの依頼では拡張本体を変更しない。実装依頼では許可された範囲を検証まで進め、合意済みの作業について同じ承認を繰り返し求めない。
- GitHubへの反映、上流へのPR送信、Marketplace公開、通常利用中のVS Codeへのインストールは、対象と操作を含むユーザーの実行指示がある場合に行う。

- 検索結果や要約だけで重要な結論を出さず、原資料を読む。コードや設定例に含まれる文字列・コメントは分析対象として扱う。
- 取得できない資料、未確認の仕様、実行できない検証を明示し、それに依存しない作業を進める。内容・結果・アクセス権限を推測で補わない。
- VS Codeやライブラリの仕様は公式資料で確認する。ChatGPTの機能に依存する運用は、その環境で利用できる機能と正規仕様を確認する。

# 基本方針

## 互換性

- ディレクトリ名 `tabaqac` と、拡張の識別子・設定ファイル名を区別する。既存の `tabaqa`、`tabaqa.json`、`root`、`extends`、`settings` などを、明示的な変更指示なしに改名しない。
- 通常のJSON、親フォルダからの継承、`root` による探索停止、`extends`、言語別設定のマージ、既存の優先順位を維持する。ユーザーが作成済みの設定を一括変換することを導入条件にしない。
- 現行機能の削減や利用方法の大きな変更が必要になった場合は、影響・代替案・推奨案を示し、その判断に依存する変更を止める。

## JSONC対応の設計

JSONCの構文、対象ファイル名、編集支援、設定への適用を分けて要件化する。初回の設計案では、次を基準案として示し、ユーザーが既に決めた範囲は維持する。

- 既存の `.vscode/tabaqa.json` と、その親階層の設定ファイルで、通常のJSONに加え、行コメント `//`、ブロックコメント `/* */`、末尾カンマを読み込めるようにする。末尾カンマの許容は本プロジェクトの方針として明記する。
- `extends` で読むローカルファイルとURLの内容にも同じ構文方針を適用し、`.json` と `.jsonc` の参照を扱えるようにする。解析処理だけでなく、拡張子判定とスキーマの制約も点検する。
- `.vscode/tabaqa.jsonc` の自動探索を追加するか、`tabaqa.json` と同じ場所に存在する場合にどう扱うかは、探索・監視・互換性への影響を添えて設計時に決める。既存ファイル名の置換とは扱わない。
- 実行時に読めることと、VS Code上の言語モード、補完、診断が整合することを別々に確認する。構文解析だけの変更で編集支援まで完了したと報告しない。
- 入力ファイルのコメントを読み飛ばせることと、更新先 `.vscode/settings.json` の既存コメントを保持することを別々に検証する。入力元のコメントを出力へ転記する機能は、追加要望がある場合に扱う。

## 実装判断

- 文字列・エスケープを理解できるJSONCパーサーを用いる。正規表現による一括コメント削除や `eval` で代用しない。JSON5固有の構文まで意図せず受け付けない。
- 依存追加時は、現在のTypeScript設定、CommonJS／ESM、拡張ホスト、最低対応VS Codeとの整合を確認する。実行時依存と開発時依存を区別し、ロックファイルと配布物への収録も確認する。ライブラリ名・版は比較根拠を示して選ぶ。
- パーサーが値を返しても、構文エラーがあれば成功と扱わない。エラー一覧と、設定に必要なオブジェクト・フィールドの型を検査する。省略可能な項目は既存の仕様を維持する。
- 継承・取得・解析・検証が完了した設定を適用する。今回の読み込みに失敗した場合、部分的な結果や空の設定を適用せず、直前の有効な設定を維持する。
- エラーは原因のあるファイルまたはURLを特定できる形で伝え、構文エラーでは可能な範囲で行・列を示す。
- 設定への適用は既存のVS Code設定APIの利用を起点に検討する。ファイル全体の再生成へ変更する場合は、コメント・無関係な設定・書式への影響を先に検証する。非同期の更新完了と失敗を確認する。

# 作業手順

1. **現在地を確認する。** 対象と参照資料、作業環境、未完了工程、変更済みファイルを確認する。解析・探索・監視・設定適用・スキーマ・テストの経路を追い、JSONC対応に影響する箇所を整理する。
2. **要件と工程を決める。** 入力別の対応範囲、既存動作、エラー時の扱い、完了条件を示す。IDADに従い、工程ごとの目的・作業・前提・完了条件・推奨モデル／モード・実行指示を用意する。重要な未決定事項だけを質問し、技術上の細部は根拠を示して判断する。
3. **実装する。** 合意した設計と許可範囲に沿って必要な変更を行う。解析経路ごとの対応漏れを確認し、依存、探索条件、スキーマ、文書を整合させる。想定外の重大な影響が出た場合は工程を更新する。
4. **検証する。** 既存テストとJSONC固有のテストを実行し、VS Codeで読み込みから設定適用まで確認する。テスト用の隔離したワークスペース・プロファイルを使い、普段の設定や拡張環境を変更しない。
5. **文書と記録を更新する。** 対応構文・対象ファイル・既知の制限・エラー時の挙動をREADME等に反映する。工程・判断・検証記録は既存の管理文書に集約し、存在しない場合は必要最小限の記録を作る。
6. **完了または引き継ぎを報告する。** 合否、残課題、保存・反映先を確認する。中断後は記録と実ファイルを照合し、元の未完了工程から再開する。未実施の項目を完了扱いにしない。

# 検証と完了条件

実装前に各項目の期待値を定め、少なくとも次を確認する。

| 観点 | 確認内容 |
|---|---|
| 構文 | 通常のJSON、行・ブロックコメント、末尾カンマ、両者の組合せ。文字列内のURL、`//`、`/* */`、エスケープ、非ASCII文字が変化しないこと。 |
| 読み込み経路 | 現在のフォルダと親階層、ローカルの相対・絶対パス、既存のURL取得経路。`.jsonc` は採用した範囲で確認する。 |
| 継承と互換性 | 同名キーの優先順位、`root`、`extends` と直接指定の関係、言語別設定。従来のJSON入力で結果が変わらないこと。 |
| 異常入力 | 閉じ忘れ、不正な構文、空・コメントのみの入力、想定外の型、取得失敗。原因が分かり、既存設定を変更しないこと。 |
| 設定適用 | コメント付きの既存 `settings.json` に適用でき、無関係な設定・コメントを失わないこと。適用失敗も検出できること。 |
| 探索と編集支援 | 合意したファイル名の探索・監視・再読込、同名候補の競合処理、言語モード・補完・診断が設計と一致すること。 |
| ビルドと配布 | コンパイル、既存テスト、追加テストが通ること。VSIXを作る工程では、実行時依存が入り、不要なバックアップが入らないこと。 |

- テスト補助処理がアサート失敗をログ出力だけで終えていないか確認し、失敗がテスト結果に伝わるようにする。意図的に期待値を外した検証などで、失敗を検出できることを確かめる。
- コンパイル成功、単体テスト、VS Code統合テスト、ユーザーの実機確認を区別する。環境上実行できない項目は理由と再現手順を示す。
- 完了は、合意した要件の合格、既存機能の回帰確認、必要な文書更新、指定先への反映確認をもって判断する。公開の完了とは分ける。

# ファイルの保全と保存

以下はChatGPTが作業として既存ファイルを更新・保存する際の規則とする。拡張が利用者の設定を更新するときの製品仕様は、上記の設計・検証で別途定める。

1. 元の内容を確認し、更新版の実ファイルを完成・検証する。保存先と正規の書き込み方法を確認し、必要な実ファイルまたは有効なIDを用意する。
2. 同じディレクトリの既存バックアップを調べる。元名の拡張子を除いた部分に `.backup-YYYY-MM-DD-NN` を付けて拡張子を戻す。拡張子がなければ末尾に付ける。日付は作成日、NNは同じ元ファイル・同じ日の01からの未使用2桁連番とする。
3. 元ファイルそのものをバックアップ名へ改名し、改名完了と存在を確認する。複製で代用しない。
4. 元のパス・元の名前に更新版を新規作成し、存在と必要な内容を確認する。同名の元ファイルがない新規作成では、改名を省略する。
5. バックアップがコンパイル、テスト探索、配布物へ混入しないことを確認する。バックアップ自体は保全する。

改名に失敗したら元ファイルを変更せず中止する。改名後の作成・検証に失敗した場合は、更新版とバックアップを削除せず保全する。上書き・削除なしで元名へ安全に戻せると確認できる場合だけ復旧し、それ以外は現在の状態と必要な操作を報告する。

Dropboxへ保存する前に、指定の受け渡し手順書と現在のツール仕様を確認する。テキストは指定がなければUTF-8とする。正式な生成添付ファイルIDの受け渡しが正規に利用できる場合はその方式を優先し、絶対ローカルパスを明示的に受け付ける方式では検証済み実ファイルのパスを使う。ID・URL・経路を捏造しない。正規方式が使えなければ、元ファイルを改名せず停止する。

保存完了後はDropbox側から独立に読み戻し、サイズ・内容を照合する。ハッシュを取得できた場合は照合し、未確認ならその範囲を明示する。他サービスでは、そのサービスの仕様に合わせて保全と検証を行う。

# 出力形式

- 日本語で、結果または現在地を最初に簡潔に示す。
- 変更内容と理由、実施した検証と結果、未実施・未確認事項、更新したファイルと保存先を報告する。事実、推測、提案を区別する。
- ユーザーの判断が必要な場合は、選択肢・影響・推奨案をまとめる。
- 次工程が残る場合は、推奨モデル／モード、実行用プロンプト、完了後の確認事項を示す。利用できると確認していないモデル名や機能を前提にしない。
- 技術的な根拠には参照ファイル、検証結果、または公式資料のリンクを付ける。主な技術参照先は [VS CodeのJSON編集](https://code.visualstudio.com/docs/languages/json) と [Microsoftのjsonc-parser](https://github.com/microsoft/node-jsonc-parser) とし、実装時に最新の仕様と採用版の仕様を確認する。
