# このプロジェクトの目的

VS Codeのワークスペース内のYAML・Markdown・Plaintextを、ユーザーが作成するJavaScriptでMarkdownへ変換し、VS Code標準のMarkdownプレビューへ手動で表示・更新する独立した拡張機能「Markdown Preview via JS Transforms」を開発・保守する。

変換処理の自由度と、ユーザーが実行するまで変換結果が変わらない操作感を守り、設計・実装・検証・導入可能な成果物の提供まで担当する。

# 対象と範囲

- 開発作業フォルダは `Dropbox\www\studio\markdown-preview-via-js-transforms`。以下、`<開発ルート>` と呼ぶ。
- `<利用ワークスペース>` は、拡張機能の利用者がVS Codeで開き、入力ファイルと変換JavaScriptを置く場所を指す。`<開発ルート>` と混同しない。
- 対象は要件整理、技術調査、設計、実装、テスト、不具合修正、文書整備、VSIXの作成、導入・実機確認の支援。
- 業務や作品に固有のYAML解析・Markdown整形など、変換処理そのものはユーザーが作成する。別途依頼されるまでは、入力文字列をそのまま返す動作確認用サンプルだけを提供する。テスト用の異常系スクリプトはこの制限の対象外とする。
- 自動変換、独自Markdownレンダラー、Web版への対応などは初期要件に追加しない。必要性が判明した場合は、影響を説明して採否を確認する。

# 必須要件

## 1. 入力と変換処理の分離

- 入力はYAML（`.yaml`、`.yml`）、Markdown（`.md`）、Plaintext（`.txt`）。いずれもテキストとファイルパスをJavaScriptへ渡す。
- YAMLの解析や用途別のMarkdown生成は変換JavaScriptが担う。拡張機能は、対象の選択、実行制御、結果の検証、プレビュー連携、エラー表示を担う。
- `<利用ワークスペース>` 内の指定フォルダに複数の変換JavaScriptを置けるようにする。配置例は `transforms/` とし、採用する指定方法と候補の探索範囲を文書化する。
- 変換JavaScriptの追加・変更に、拡張機能の修正・再ビルドを要求しない。次の手動実行時に保存済みの変更が確実に反映されるよう、読み込みとキャッシュの扱いを検証する。
- インターフェースは入力の `text` と `filePath`、出力のMarkdown文字列を基本とし、非同期処理を扱える簡潔な契約にする。次は原案の参考形式であり、モジュール方式は工程1・2で確認して決める。

```javascript
module.exports = async function ({ text, filePath }) {
  return text;
};
```

- 外部npmライブラリの利用方法、依存関係の配置・解決、実行環境を検討し、採用方式または制約を説明する。拡張機能側と変換処理側の依存関係を区別する。
- 入力の未保存編集、未保存のJavaScript編集、ワークスペース未使用時、複数ルートの扱いは設計段階で決め、利用者が「何が実行されるか」を予測できるようにする。未決事項を実装済みの仕様として報告しない。

## 2. 手動実行コマンド

| コマンド | 必須の動作 |
|---|---|
| 変換処理を選択して実行 | 開いている対応入力ファイルを対象に、JavaScript候補を表示し、選択した処理を実行してプレビューを表示・更新する |
| 前回の変換を再実行 | 前回の入力ファイルと変換JavaScriptの組を再利用し、再選択なしで実行する |

- 両方をコマンドパレットから使用でき、キーボードショートカットを割り当て可能にする。
- 再実行では、現在アクティブな別ファイルやプレビューを入力に取り違えない。実行対象と前回の記録を更新するタイミングを定義する。
- 前回の記録がない、候補がない、対象が消失した、選択をキャンセルした場合は、原因や次の操作を示して終了する。キャンセルを変換成功として扱わない。
- 連続実行時の競合を制御し、古い実行結果が後の結果を上書きしないようにする。

## 3. プレビューと更新条件

- 原則としてVS Code標準のMarkdownプレビューを使う。工程1で「標準プレビュー」と「完全手動更新」の両立を最優先で検証する。
- 入力や変換JavaScriptの変更・保存・自動保存を変換実行の契機にしない。自動保存設定も変更しない。
- 明示的な実行時に入力を取得し、変換が成功してMarkdown文字列であることを確認してから、表示用の結果を差し替える。
- プレビューの再表示や内部的な内容取得を理由にJavaScriptを再実行しない。表示用のMarkdownは、次の手動実行が成功するまで前回成功時の内容を保持する。
- 実行失敗・中断時は、前回成功したプレビューを保持する。初回失敗時も、失敗を成功した空の出力と区別する。
- 生成Markdownを利用ワークスペースに残さない方式を優先する。ただし標準機能との互換性、安定性、保守性を優先して選ぶ。
- 仮想文書・一時ファイルなどの方式を先に固定せず、プレビュー更新、相対リンク・画像、再表示、後始末への影響を確認する。原案から重要な差異が生じる場合は採否を確認する。

## 4. エラーと安全性

- 入力・JavaScriptの不存在、構文エラー、実行例外、文字列以外の戻り値、終了しない処理を検出・処理する。
- 処理が終わらない場合にVS Codeの操作へ戻れるよう、制限時間や中断方法を設計する。同期的な無限ループと完了しない非同期処理の両方を検証し、見かけ上の待機終了だけで済ませない。
- 原因、対象ファイル、修正や確認に必要な情報を表示し、詳細な診断情報を確認できるようにする。
- Workspace Trustを考慮し、未信頼のワークスペースでは変換JavaScriptを無条件に実行しない。
- ユーザーの元入力と変換JavaScriptを、拡張機能が自動で上書き・整形・保存しない。
- 任意JavaScriptの実行権限と制限を明記する。実行処理の分離や信頼確認だけを根拠に、安全なサンドボックスであると説明しない。

# 受入条件

変更内容に応じて、次を検証する。自動テスト、拡張機能としての検証、ユーザー実機での確認を区別する。

- 対応する4拡張子をテキストとして処理し、文字化けや意図しない入力書換えがない。
- 複数JavaScriptを選択でき、再実行では前回の入力と処理の組を使う。
- 入力とJavaScriptを編集・保存・自動保存しても、変換回数と生成Markdownが変化しない。
- 手動実行で最新の対象内容が使われ、JavaScriptの保存済み変更が再ビルドなしで反映される。
- プレビューがアクティブでも再実行でき、再表示だけで変換が走らない。
- 対象の消失、構文エラー、例外、不正な戻り値、無限ループ・未完了非同期処理で、前回成功した結果が失われず、再試行できる。
- 未信頼のワークスペースでJavaScriptが無条件に実行されない。
- 連続実行、候補なし、初回失敗、選択キャンセルを処理できる。
- 採用したnpm利用方法、相対リンク・画像の扱い、複数ルートなどは、対応範囲内で確認する。
- 作成したVSIXを用いる導入・操作の確認方法があり、実施結果と未実施項目が分かる。

# ファイル保全と保存

- 作業は指定範囲で行い、無関係なプロジェクトやユーザーの変更を巻き戻さない。GitHubとの対応は索引や確認済みの設定に基づき、名前から推測しない。公開、配布範囲、ライセンスの変更はユーザーの判断に従う。
- 新規ファイルは同名の既存ファイルと保存先を確認して作成する。テキストは指定がなければUTF-8とする。
- 既存ファイルの更新では、更新版を先に完成・検証し、正規の書き込み方法と必要な実ファイル・IDを用意する。その後、同じディレクトリのバックアップ名を確認し、元ファイルそのものを `元名.backup-YYYY-MM-DD-NN.拡張子` へ改名する。拡張子なしなら末尾に付ける。日付は作成日、NNは同じ元ファイル・同じ日の01から始まる2桁の未使用連番とする。
- 改名完了とバックアップの存在を確認してから、元のパス・元のファイル名に更新版を新規作成し、存在と内容を確認する。複製、直接上書き、Git履歴を、このバックアップの代わりにしない。
- 改名に失敗したら元ファイルを変更せず中止する。改名後に保存・検証が失敗したら、更新版とバックアップを削除せず保全する。上書き・削除なしで安全に戻せると確認できる場合だけ元名へ復旧し、それ以外は現在の状態と復旧手順を報告する。
- Dropboxへの保存・同期前は、ChatGPT Libraryの `/references/chatgpt-file-handoff-to-dropbox.md` を取得し、現在のツール仕様と併せて確認する。正式な生成添付ファイルIDを渡せる仕様なら優先し、絶対ローカルパスを明示的に受け付ける仕様ならその方式を使う。ID・URL・経路は捏造しない。正規方式を確認できなければ既存ファイルを改名しない。
- 保存完了後はDropbox側から独立に読み戻してサイズ・内容を照合し、ハッシュを取得できた場合はそれも照合する。保存と検証の成功を区別し、未検証を成功と報告しない。
