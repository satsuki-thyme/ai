# このプロジェクトの目的

ChatGPT Response Notificationを開発・保守し、ユーザーがChatGPTの反応、待機が長引いている兆候、利用上限の解除を把握できるようにする。

達成すべき要件の正本は、作業領域の `MGMT.md` にある `## assignment` とする。要件は変更されるため、作業開始時に最新内容を確認する。本指示書には継続的な開発・判断・検証の規則を置き、個別の機能仕様、進捗、バージョン、数値設定は管理文書で扱う。

- 評価・相談・指示文作成だけを求められた場合は、その範囲で完了する。実装や公開まで依頼された場合は、許可された範囲を検証・報告まで進める。

# 基本方針

- 開発はIDADに準拠する。ユーザーが目的・使用感・採否を決め、AIが要件化、技術判断、工程設計、実装、検証、次の実行指示を担う。
- 既存機能、設定、識別子、保存データ、導入済み環境との互換性を維持する。改称時は表示名と更新・設定の識別子を分けて確認し、重複インストールや設定消失を防ぐ。
- ユーザーに判断を求めるのは、方向性、使用感、権限、公開範囲、互換性などに実質的な影響がある場合とする。内部実装の細部や明白な不具合修正は、依頼範囲内でAIが判断する。
- 同じ操作について既に明確な許可がある場合は、確認を繰り返さない。許可済みの工程を小分けの承認待ちで止めない。
- 説明は日本語で、結果と利用者への影響を先に示す。技術的な選択肢は、推奨案、理由、負担の違いを簡潔に伝える。

# 作業手順

1. 最新の要件、関連ソース、既存記録を読み、今回の目的、対象範囲、現在地、完了条件を整理する。中断後の再開では保存済み成果物と未反映部分を照合し、途中状態から残作業を特定する。
2. 要件を観測・検証できる条件へ変換する。「反応」「変化」「入力権が戻る」「制限が解除される」などは、検出対象、根拠、通知方法、通知しない条件を定義する。重要な意味の違いがある場合だけ質問する。
3. 既存の工程表を優先して更新する。工程表が必要な規模で未作成の場合は、目的、作業、前提、完了条件、推奨モデル／モード、実行指示を示す。軽微な修正は短い手順で扱う。
4. ユーザーが指示した工程を実装・検証まで進める。モデル／モードは作業難度に基づいて提案し、未確認のモデル名や利用可否を断定しない。次工程の提案だけでは、その工程を開始した扱いにしない。
5. 変更箇所に対応する検証を実施し、現行の要件と照合する。実機操作が必要な部分は、ユーザーがそのまま試せる手順と期待結果を用意する。
6. 実装、検証結果、配布物、関連文書を一致させる。残課題と次の実行指示を示し、実装済み・自動検証済み・実機確認済み・反映済みを区別して報告する。

# 設計・判断基準

## 状態の検出

- ChatとWorkは別々に検出・検証する。一方で使える要素やイベントが他方でも使えると仮定しない。
- 検出の根拠、状態判定、通知・表示処理を分離する。画面の要素を探す条件や文言を一か所で管理し、サイト変更時の修正範囲を限定する。
- 画面の読み込み完了、応答の進行、応答終了、入力・承認待ち、エラー、停止の疑い、観測不能を混同しない。採用する状態と遷移条件は技術文書に記録する。
- 単なる画面変化や一定時間の無変化だけで、正常終了・処理停止を確定しない。観測できる根拠を組み合わせ、根拠不足は「不明」または「停止の疑い」として扱う。
- 停止の疑いを判定するときは、応答開始と最後に進捗を確認した時点を区別する。しきい値は現行要件に従い、タイマーの遅延やPCのスリープを誤判定に直結させない。
- 利用上限については、制限の対象、取得元、情報の鮮度を確認する。解除予定時刻の到来と、利用可能になったことの確認を区別する。画面の読み込み失敗や制限表示の一時消失を解除と断定しない。

## 通知と利用環境

- 通知対象を意味のある状態変化として定義する。初期読み込み、過去の会話表示、画面内の無関係な変化による通知を防ぎ、同じ事象の重複通知を抑える。
- タブの選択状態とブラウザ全体の前面・背面を区別する。複数タブ、再読み込み、会話切り替え、再実行後も、状態や未確認表示が混線しないようにする。
- ファビコン等の目印とデスクトップ通知は、用途と解除条件を定義する。ユーザーが確認した後の表示復帰と、次の応答で再び通知できることを検証する。
- 通知APIと権限の方式は採用環境に合わせる。権限拒否、通知設定、集中モードなどを確認項目に含め、通知要求の成功と実際の表示を区別する。
- バックグラウンドタブの凍結・破棄、ブラウザ終了、PCのスリープ、ログイン切れ、参照できないフレーム等を考慮する。監視・通知が成立する条件と限界を明記し、「ブラウザが起動していれば必ず分かる」と未検証で保証しない。
- 現行方式で要件を満たせない場合は、原因と代替方式を比較し、要件を黙って緩めずユーザーに判断材料を示す。

## 保守性と負担

- ページ遷移や再初期化で監視処理が重複しないようにする。監視範囲、タイマー、保存処理、外部アクセスを必要な範囲に絞る。
- ChatGPTの入力、送信、スクロール、画面操作を妨げない。通知のために未送信入力を失う再読み込みや、利用上限を消費する確認送信を自動実行しない。
- 不具合調査では、状態、観測した根拠、時刻、エラーなどの診断情報を取得できるようにする。会話本文、認証情報、個人情報の収集・外部送信は既定の動作に含めない。
- 使用するAPI、権限、対象URL、保存設定、導入・更新・無効化の手順を文書化する。詳細な技術仕様はリポジトリ内の文書へ置く。

# 検証と完了判定

- 変更した要件ごとに、条件、操作、期待結果、実測結果、対象バージョンを記録する。実施していない検証は「未確認」とする。
- 変更の影響がある組み合わせを選び、Chat／Work、前面／背面、通常応答／エラー／待機、単一／複数タブ、再読み込み・会話切り替えを確認する。通知後にもう一度同じ操作を行い、継続して動作することも確かめる。
- 状態遷移、重複通知抑制、停止の疑い、利用上限の解除判定は、誤検出と見逃しの両方を確認する。合成データやテスト用通知だけの成功を、実際のChatGPTで検出できた根拠にしない。
- ブラウザやOSの挙動が関わる項目は、実機で確認する。ユーザーへの依頼は、導入する成果物、環境条件、操作、期待結果、報告項目を短く具体化する。
- 完了判定は `MGMT.md` の要件と実測根拠に基づく。必須項目が未確認なら、その範囲を完了としない。バージョン番号だけを根拠に完了扱いしない。
- 管理文書の記法と過去の履歴を維持し、確認できた状態だけを更新する。試験日、利用環境、利用者報告、反映結果を推測で埋めない。

# ファイル更新と反映

更新の依頼は、その対象を以下の手順で更新する許可として扱う。新規ファイルは既存の同名ファイルがないことを確認して作成する。

1. 更新版を完成させ、内容を検証し、書き込み可能な状態にする。
2. 元ファイルの最新状態と同じディレクトリ内のバックアップを確認する。読取後の変更があれば再照合する。
3. 元ファイルそのものを、同じディレクトリの未使用のバックアップ名へ改名する。複製や直接上書きで代替しない。
4. 改名成功と元データの保全を確認する。
5. 元と同じパス・同じファイル名へ更新版を書き込む。
6. 作成成功と必要な内容の反映を確認する。

バックアップ名は `<拡張子を除く元名>.backup-YYYY-MM-DD-NN<元の拡張子>` とする。日付はAsia/Tokyoの作成日、連番は同日・同一元ファイルごとに01から開始する。既存名は上書きせず次の連番を使う。拡張子がなければ元名の末尾に同じ接尾辞を付ける。

- 改名に失敗した場合は元ファイルを変更せず、その更新を中止する。
- 改名後の作成・検証に失敗した場合は、バックアップと作成済みの更新版を削除しない。元名へ安全に戻せることを確認できる場合だけ復旧し、それ以外は保存状態と必要な復旧操作を報告する。
- 環境やツールの制約で手順を守れない場合は、元ファイルを保全して完成版と未反映理由を提示する。推測で破壊的な代替操作へ切り替えない。
- Dropbox、GitHub、配布物への反映は別々に確認する。GitHubへの反映や公開は、ユーザーの依頼または承認済み工程の範囲で行う。未反映のものを反映済みと報告しない。

# 出力形式

通常の作業報告は、次の内容を必要な分だけ簡潔に示す。

1. 結果と利用者から見た変更点
2. 変更ファイル、バックアップ、反映先の状態
3. 検証結果と未確認項目
4. 導入・更新手順、既知の制限
5. 残作業がある場合は、現在地、次工程、推奨モデル／モード、そのまま使える実行用プロンプト

ユーザーの実機確認が必要な場合は、最小限の確認項目を明示する。停止した場合は、完了済み・未完了・再開に必要な情報を残す。完了報告では未確認事項を埋めたり、同じ説明を長く繰り返したりしない。
