# このプロジェクトの目的

`Dropbox\www\studio\character-relationship-chart` の「Character Relationship Chart」を継続的に発展させる。人物・グループ・関係を整理する利用者の使いやすさ、既存データの保全、保守しやすさを重視する。

廉価・軽量モデルから高性能・高推論モデルまで共通して使う。必須の品質条件を維持し、作業の分割と調査の深さを難度に合わせる。

# 対象と範囲

- VS Code拡張と独立Web版の相談、調査、設計、実装、検証、文書整備、配布準備を扱う。ソース、データ仕様、GUI、テスト、配布物、確認済みの対応リポジトリを対象とする。
- 相談・評価・計画だけの依頼ではファイルを変更しない。実行依頼では、指定範囲の実装・検証・成果物の提供まで進め、計画だけで終えない。
- 工程表の次工程、過去の提案、`MGMT.md` の未完了項目は、自動的な実行許可ではない。`assignment` は退避中の課題として扱い、ユーザーが指定した場合に実行対象へ戻す。

# 全モデル共通の必須ルール

1. 更新前に、対象の原文、反映先、依頼範囲、完了条件を確認する。未読のファイルや存在未確認の機能を推測で書き換えない。
2. 既存データ、作業中の差分、未保存入力を保護する。開発中の既存ファイルは「ファイル更新」の改名バックアップ手順で更新する。
3. データ形式・識別子・利用者の操作を変える判断と、既存設計に沿う内部実装の判断を分ける。重要な方針変更は影響と推奨案を示して確認する。
4. 実施した検証と未実施の検証、作業用コピーと実際の反映先、配布物作成と公開を区別する。成功は実際の結果で判断する。
5. 不明点は、その点に依存しない作業を進めたうえで確認する。モデル名や自己評価だけを理由に必須確認を省いたり、作業全体を停止したりしない。

# 開発運用方式と作業手順

「意図主導型AI開発（Intent-Driven AI Development / IDAD）」に準拠する。正本は `Dropbox\ai\development-and-operations-model\idad-v1.md`。開発着手時に参照し、工程の見直し・再開時は更新を確認する。正本を読めない場合は未確認と明示し、以下の確認済み手順で進められる範囲を進める。

ユーザーは目的・好み・制約・採否を決め、AIは要件化から検証、次の指示文まで担う。共通方式はIDAD、仕様は技術文書、進捗は工程表に置く。

1. **目的と現状をそろえる。** 依頼を相談・計画・実装・配布・公開に分け、対象、望む挙動、維持する制約、完了条件を特定する。不具合では再現条件を調べ、報告・確認事実・仮説を分ける。
2. **最小の作業単位を決める。** 関係する入力・出力・呼出元・保存先を確認する。既存の工程名と番号を維持し、目的／主な作業／前提・依存関係／推奨モデル・モード／作業量／完了条件を工程表に整理する。軽微な変更は一工程でよい。
3. **判断を確定する。** 内部実装は既存様式を尊重してAIが選ぶ。製品の方向、使い勝手、機能削除、互換性、公開範囲、ライセンス、プライバシー、保守方針に大きく影響する変更は、推奨案と影響を示す。確認済みの判断や許可を聞き直さない。
4. **許可された範囲を実装する。** 一単位ごとに変更・検証・記録をそろえる。複数ファイルで一つの仕様を実現する場合は一組として扱い、解析・Schema・GUI・テスト・文書の一部だけを変更した状態で完了にしない。
5. **完了条件を照合する。** 「検証と配布」に沿って確認し、重大な保存・互換性の問題を修正する。新しい問題や予定との差を整理し、現在の記法を維持して工程表と関係文書を更新する。
6. **結果と次の指示を渡す。** 指定範囲が終わったら到達点を報告する。次工程は実行用プロンプトとして提案し、未依頼の工程には着手しない。

質問は、答えによって成果物や安全な実行方法が大きく変わる場合に限り、一度に最大3問とする。軽微な不足は既存規約に沿う前提で補って報告する。重大な想定外は、影響する作業を止め、残せる成果と工程修正案を示す。

# モデルの性能差に合わせる方法

## 工程の選び方

モデルの固定名より、作業の難度と必要な推論量を基準にする。工程開始前に推奨と理由を短く示す。

| 作業条件 | 推奨 | 作業の組み立て方 |
| --- | --- | --- |
| 仕様・対象・期待結果が確定した文書修正、定型置換 | 廉価・軽量 | 対象と変更規則を明示し、差分を確認する |
| 既存設計に沿う機能追加、不具合修正、テスト | 標準 | 関連する処理とテストを一組にし、通常系・失敗系を確認する |
| 複雑な原因調査、複数環境にまたがる設計、保存・競合・移行の設計変更 | 高性能・高推論 | 先に契約・状態遷移・失敗時の保持を整理し、検証可能な単位へ分割する |

- 上表は推奨であり、モデルごとの実行禁止ではない。軽量モデルでも複雑な依頼を調査・設計・局所実装・統合確認へ分けて進める。高性能モデルでも必須ルールは省かない。
- 各単位には「入力資料」「変更対象」「期待する結果」「検証方法」「次へ進める条件」を持たせる。高性能モデルの実装手段や内部の考え方まで固定せず、この条件を満たす方法は任せる。
- 複数の責務を同時に変える、前提が未確定、関連資料を一度に扱いきれない場合は分割する。ただし検証できない未完成状態を成果物として渡さない。許可済み範囲は同じ作業内で続行できる。
- 原因の裏付けがない、重要な整合性を確認できない、同じ失敗が新しい根拠なく続く場合は、変更を広げず問題を切り分ける。解消できない部分は上位モデルによる確認を提案し、参照先・確認事実・未解決点・次の検証を引き継ぐ。
- モデルの性能不足とツール・権限・実行環境の不足を区別する。モデル変更だけではアクセス不能や実機未確認は解消しない。
- 実行モデル・推論設定は確認できる情報だけで述べ、切替の提案を切替済みとしない。具体名が不明なら上表の区分を使う。
- ChatGPT Plusの利用枠は、参照範囲と重複作業を減らして節約する。消費量・残量・回復時刻は推測で断定しない。保存保護と必要な検証は省かない。

## 中断・再開・モデル変更

中断時や別セッションへ渡す際は、目的／現在の工程／確定した制約／参照先／変更ファイルと反映先／検証済み・未検証／未完了事項／次の一手を残す。内部思考の逐語的な記録は求めず、判断の結論と根拠を簡潔に示す。

再開時は現行ファイル・差分・記録を照合し、元の工程の完了を優先する。実装済みでも実機確認待ちなら、その状態を維持する。途中状態を新しい仕様にしたり、完了済みの変更を再適用したりしない。

# 設計・実装の判断基準

## 基本方針

- 日本語で率直に、結論と利用者への影響を先に伝える。称賛や長い前置きを避け、技術的な選択肢は使い勝手・互換性・作業量・保守への影響で説明する。
- 既存の構成・命名・実装様式を尊重し、目的を満たす最小限の変更を選ぶ。大規模再編や新しい依存は具体的な利点がある場合に提案する。
- 表示名は `Character Relationship Chart`。拡張ID・コマンドID・データキーは現行コードを正本とし、合意なしに改名しない。廃止済みの個人用名称を再導入しない。
- アプリの版数・対応環境は現行manifest・lockfile・配布資料で確認し、固定値をこの指示書に持ち込まない。アプリ版数とデータ形式の `version` を区別する。
- ローカル利用、オフライン利用、人物データを外部送信しない性質を維持する。外部通信を導入する場合は目的・送信内容・必要性を示して合意を得る。

## データと保存

- 任意名の `.jsonc`、本体と表示データの分離、`<本体ファイル名>.view.json` の対応を維持する。例：`人物.jsonc` と `人物.jsonc.view.json`。
- 人物・グループのIDと表示名を区別し、複数所属、関係参照、保存済み配置を保つ。ID変更・削除では関連データへの追従を確認する。
- JSONCの変更対象外のコメント・整形を一括して失わない。型・参照先・重複・項目間の整合性を実装側でも検証する。存在しない仕様や未対応フィールドを実装済みとして扱わない。
- 外部編集、未保存変更、不正データ、書込失敗、保存結果不明を区別し、元データとGUI入力を保持する。競合や確認不能のまま上書きせず、退避・再読込の経路を示す。
- Web版では、明示的な直接保存とダウンロードを区別する。非対応・権限拒否・失敗時のダウンロード経路を維持する。保存済み判定は実際の保存・照合結果に基づけ、ダウンロード開始だけで保存完了としない。
- 確認できない完全排他・原子性を保証しない。既存データを読めなくする変更は、理由・影響・移行方法を先に示し、旧データと移行後のデータを検証する。
- 製品が利用者のデータを保存するときは自動バックアップを作らない。これは、AIが開発ファイルを更新する際の改名バックアップとは別の規則である。

## 描画・環境別処理

- 変更に関係する直線・曲線・自動、線種、矢印、複数関係、自己関係を回帰確認する。色だけに依存しない識別、テーマ、拡大縮小、狭い画面での操作を考慮する。
- 描画計算の成功と見た目・操作の成功を分ける。保存、開き直し、提供済みのSVG出力まで、影響する利用の流れを確認する。
- 入力文字列をHTML・スクリプトとして実行しない。Webview・ブラウザとの境界でメッセージと保存対象を検証する。
- 共通 `core` と `ui`、環境別アダプターを目標とし、現行構成と `docs/architecture.md` を照合する。`core` はVS Code・DOM・ブラウザ固有APIに依存させず、共通UIはホストとの入出力を分離する。
- 保存、表示データ、Undo、競合検知は両環境の提供状況・制限を別々に確認する。一方の実装や試験の成功を他方へ一般化しない。
- `packages/`・`apps/` の再編は必要な段階で行い、未使用の抽象化を増やさない。内部モデルの名称を理由に外部キーを変更せず、各段階で既存VS Code版と提供済みWeb機能を維持する。

# ファイル更新と外部への反映

実行依頼に必要な通常の作成・編集・検証・配布物作成は、依頼の範囲で進める。Git操作や公開は対応先があるだけで実行せず、依頼または既に確認済みの運用上の許可に従う。環境が要求する承認は守り、同じ許可を重ねて求めない。

## 既存ファイルの更新

`.git` の有無を問わず、次の順序を守る。コピーによるバックアップや直接上書きで代替しない。

1. 更新内容を完成させ、元ファイルを変更せずに書き込める状態へ準備する。
2. 同じディレクトリの既存バックアップを確認し、`<拡張子を除いた名前>.backup-YYYY-MM-DD-NN<元の拡張子>` を決める。日付は作成日の `Asia/Tokyo`、連番は同じ元ファイル・同じ日で `01` から未使用の次番号とする。拡張子がなければ元名の末尾に付ける。
3. 更新直前の元ファイルを取得時の内容・版と照合する。外部変更があれば取り込み方を確認し、古い内容で更新しない。
4. 元ファイルそのものを同じディレクトリのバックアップ名へ改名する。
5. 改名成功と元データの保全を確認してから、元と同じパス・名前へ更新版を書き込む。
6. 更新版の内容と反映先を検証し、バックアップを保持する。

改名に失敗した場合は元ファイルを変更せず中止する。改名後の作成・検証に失敗した場合は更新版を削除せず、バックアップを保持する。元の名前へ安全に戻せると確認できた場合だけ復旧し、それ以外は現状と復旧に必要な操作を報告する。

直接更新できない場合は元ファイルを保全し、完成した置換用ファイルと反映手順を渡す。作業用コピーやダウンロード提供だけでDropbox・GitHubも更新済みとは報告しない。
